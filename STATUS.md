### Fixed

- **[P0] N1: typing a decimal into any numeric field silently corrupted the value** (`"12.5"` → `512`, `"0.05"` → `5`, `"-2.5"` → `-2`). Root cause: every numeric field was a *controlled* `type="number"` input whose `onInput` parsed the raw value and wrote it straight back into `value` on each keystroke — Chromium's number-input value getter reports `"12"` (not `"12.""`) for the in-progress text `"12."`, so that round-trip silently dropped the decimal point and moved the caret the instant `"."` was typed, before the next digit ever landed. `fill()`-based tests (used by both the previous audit and the existing e2e suite) set a field's value in one shot and never exercised this — only real, per-keystroke typing (`pressSequentially()`/`keyboard.type()`) does.

  Fix, in `src/lib/invoice.ts` and `src/components/Editor.tsx`:
  - New pure helpers `parseDecimalInput(raw): number | null` and `formatDecimalInput(n): string` in `invoice.ts`. `parseDecimalInput` returns `null` — "leave state untouched" — for anything incomplete (`""`, `"-"`, a trailing `"."`/`","` with nothing after it), accepts `"."` always as the decimal separator and `","` as one when the string is otherwise digits-only (so `"1,5"` → `1.5`), and rejects anything with more than one separator or a non-numeric character.
  - New `DecimalField` component in `Editor.tsx` replaces every numeric `<input type="number">` with `type="text" inputmode="decimal"`. It keeps the literal string the user typed in local state and renders *that* — never a value re-derived from the document — while the field has focus (tracked via a ref, not state, to avoid re-render races); a `useEffect` only re-syncs the displayed string from the document's value when the field is *not* focused (e.g. loading a different saved document). `onCommit` fires on every keystroke that parses to a complete number, so totals stay live while typing, and once more on blur with a 0 fallback, which also reformats the field to `formatDecimalInput`'s canonical string.
  - Applied to all 8 numeric fields the audit named: line qty, unit price, per-line discount %, per-line tax %, global discount value, shipping, shipping tax %, and deposit.
  - New unit tests in `tests/unit/invoice.test.ts` for `parseDecimalInput`/`formatDecimalInput`, including a test that replays the audit's exact keystroke-by-keystroke sequences ("1", "12", "12.", "12.5", etc.) and asserts the final committed value is correct.
  - New e2e tests in `tests/e2e/editor.spec.ts` using `page.keyboard.type(...)` (real key events, not `fill()`): unit price with `"12.5"`, `"0.05"`, `"-2.5"` and `"1,5"`, asserting both the field's own displayed value and the live grand total; a second test covers quantity (`"12.5"` hours) and a sub-integer discount (`"0.5"`%) committing correctly into the totals engine.

### Fixed

- **[P1] A3-1: `parseDecimalInput` always read a lone "," as the decimal separator, so on the page's default en-US locale "1,500" (one thousand five hundred, written the standard en-US way) silently became $1.50 — a 1000x under-bill — and "1,234.56" reformatted to $0 on blur.** Root cause: the audit-2 fix for N1 added comma-as-decimal support unconditionally ("accepts ',' whenever the string is otherwise digits-only"), so it could never tell a real thousands separator from a comma-decimal locale's decimal point — both parse to "digits-only, one separator".

  Fix, in `src/lib/invoice.ts`:
  - `parseDecimalInput(raw, locale = 'en-US')` now takes the document's own locale and asks `Intl.NumberFormat(locale).formatToParts(1234.5)` which character that locale actually uses as the decimal point vs. the thousands separator (e.g. en-US: "." decimal / "," group; de-DE: "," decimal / "." group), instead of ever guessing from the string. The locale's own grouping character is stripped as formatting wherever it appears (a real thousands separator is never a digit the user meant to enter); a small set of currency symbols (`$€£¥₹₩₽¢₺₴₪`) and a leading "+" are stripped the same way; any whitespace is treated as thousands grouping too (covers plain-space grouping and a locale's non-breaking-space grouping typed as an ordinary space). What's left over must be digits plus at most one occurrence of the locale's decimal separator, or the string is rejected as unparseable — so "1,500" → 1500 and "$1,500.00" → 1500 on en-US, "1.234,56" → 1234.56 on de-DE, and "abc"/"12a"/"1.2.3" still correctly return `null`.
  - `DecimalField` (`Editor.tsx`) now takes a `locale` prop, threaded from `doc.locale` at all 8 numeric-field call sites (line qty/price/discount%/tax%, global discount value, shipping, shipping tax%, deposit), and passes it into every `parseDecimalInput` call.
